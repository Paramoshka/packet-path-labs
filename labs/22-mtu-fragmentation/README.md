# Lab 22 — MTU, Fragmentation and PMTUD

Create an MTU bottleneck and study fragmentation, DF (Don’t Fragment) and Path MTU Discovery.

## Topology

```text
h1 MTU1500 -- r1 -- MTU1200 -- h2
```

## Run

```bash
sudo containerlab deploy -t lab.clab.yml
sudo containerlab destroy -t lab.clab.yml
```

## Explore

- Ping with different payload sizes and `-M do`.
- Capture ICMP Fragmentation Needed messages.
- Compare behavior with and without DF.

## Useful checks

- `docker exec clab-pp22-h1 ping -M do -s 1400 -c 1 10.0.2.2`
- `docker exec clab-pp22-h1 tracepath 10.0.2.2`

## TCP PMTU black hole

The baseline has a 1200-byte link and a 1200-byte receiver interface, so TCP
may negotiate a small MSS and avoid the problem. For this exercise only,
raise h2's eth1 MTU to 1500; keep r1's eth2 MTU at 1200. Thus both endpoints
advertise a larger MSS than the transit path supports.

Install `iperf3` on h1/h2 and `iptables` on r1 (`apk add --no-cache ...`).
Start `iperf3 -s -D` on h2, then run a transfer from h1 to `10.0.2.2`.
Capture TCP and ICMP on r1. With ICMP allowed, TCP should adapt to the path MTU.

On r1, add `iptables -I OUTPUT -p icmp --icmp-type fragmentation-needed -j DROP`.
Use a fresh h2 destination address (e.g. `10.0.2.3/24` on eth1) and a new
connection so the previous destination's learned PMTU does not mask the fault.
Compare a small ping with an iperf3 transfer to the new address. Capture the
handshake and large retransmitted segments; allow time for possible TCP MTU probing.
The ICMP error is generated by r1 itself, hence OUTPUT rather than FORWARD.

Remove the exact rule with `iptables -D OUTPUT -p icmp --icmp-type fragmentation-needed -j DROP`
and repeat. Explain why permitting necessary ICMP fixes discovery, while an
MSS clamp is a workaround rather than a repair of ICMP delivery.
Destroy/deploy restores MTUs, addresses and firewall rules.
